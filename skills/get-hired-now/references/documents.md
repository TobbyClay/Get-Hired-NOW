# Produce actual tailored documents

Use the host's document/PDF skills and available renderer. Read the supplied
original CV and detailed candidate evidence. The deliverable is an actual tailored
resume/cover letter or requested file, not a programming interface or a packet of
instructions telling the user to write it themselves.

1. Select a qualified exact role and preparation level. Read the job's material
   wording and candidate preferences, including language, voice and omissions.
2. Preserve the original; start a fresh role-specific document in the private
   artifact directory. Use the person's existing template if provided and suitable.
   Reuse verified family briefs, bullet banks and established builders in a new
   exact-role namespace. Even `reuse_only` produces a fresh employer/role copy;
   do not upload a different employer's branded document or overwrite the master.
3. Reorder and tighten supported experience to make relevant evidence visible.
   Preserve truthful dates, titles, scope, education and accomplishments. Use
   employer keywords only when evidence supports them. Do not create metrics,
   claim an inferred tool or present team work as sole authorship.
   Tailor the summary, skills and experience emphasis to the central responsibilities,
   rather than just changing a filename. Follow the latest date/education corrections.
   Omission of a credential is not a truthful answer of "no credential" on a form.
4. Write a concise cover letter or recruiter draft only when requested or useful
   for that application's requirements. Follow the person's supplied voice.
5. Produce the requested format with an available tool. For PDF output, extract
   text from the actual final file and check claims/content. Render paginated
   documents and visually inspect every actual page
   for layout, overflow, clipped text, contact details, employer/requisition,
   filenames and factual consistency. Re-read changed claims against sources.
6. Save the final files and an artifact manifest with exact job identity, candidate
   revision, source references, file paths, hash/version, format and QA evidence.
   Preserve submitted versions; never overwrite them with later revisions.

Review the exact final file after the last edit, not a previous preview or a builder
template. Record final SHA-256, page count when applicable, format-appropriate QA and
candidate revision. A subsequent edit invalidates the old QA. Unrendered PDFs are
not visually approved for upload; disclose the limitation and use a supported
editable format when the application and the person's instructions permit it.

If no output format was specified, use the person's existing format when supported;
otherwise provide usable editable Markdown and offer conversion only if useful.
If no PDF/DOCX tool exists, produce a usable editable Markdown/text document and
state the format limitation. Never report a PDF created or visually checked when
it was not. Use the host's file-delivery mechanism so the person can open the result.

Form answer maps retain exact question wording, proposed answer, fact source,
required/optional status, character limits and unresolved decisions. A prepared
answer map alone does not mean a live form was filled or submitted. Local files
prepared from supplied evidence can be delivered at TAILORED while live form
verification remains pending. Do not label an incomplete packet submission-ready.
