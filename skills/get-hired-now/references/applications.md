# Real form preparation and authorized applications

Use the actual browser or application tools bound in state. Follow the host's
browser instructions. The skill does not require a website-specific code adapter
when the AI can already operate the form through an authorized browser.

## Read-only preflight

Open the official exact-role form. Confirm employer/requisition and capture visible
required questions, options, conditional branches, accepted document formats,
consent language, character/file limits and access/security state. Do not type
candidate data or upload during read-only inspection. Report `visible_fields_mapped`
only for controls actually inspected; inaccessible conditional branches remain
unknown. Qualification, form feasibility and transport success are separate.

Resolve required answers from supplied facts. For a new personal question, ask
the person. For unexpected legal wording, show the exact question and request their
answer for this employer/form. Do not recycle unrelated declarations. Assessments,
personal videos and security challenges remain human gates.

## Review or use standing scope

Before transmitting candidate data, check the permission contract. In REVIEW,
present a concrete review: exact employer/role/link, actual files, answers, sensitive
or legal declarations, intended destination and any unresolved requirements. Get
the person's approval for that action. If an existing approval still covers the
unchanged packet, do not ask again.

In AUTONOMOUS, apply within the explicitly saved action grants and batch/role
scope, with auto_submit enabled. A general “get me a job” does not silently enable
it. Hard gates apply regardless of mode. Never treat this skill as overriding
the host's own tool permissions.

## Execute and persist evidence

1. Reload current state, candidate revision, exact duplicate/attempt records and
   current form. Check artifact versions and renewed consent if anything changed.
2. Reserve a unique attempt in state and save `SUBMITTING` before candidate entry,
   upload or submission. Record owner, authorized scope/approval and destination.
   No second owner may operate that requisition concurrently.
3. Use the real tool to fill supported answers, upload the actual reviewed files,
   and complete the ordinary authorized submission. Do not stop after producing
   a plan when the user authorized applying and your tools can do it.
4. If a new question, legal term, validation problem or security challenge appears,
   stop that role, capture evidence and persist its actual outcome. Ask only for
   the missing fact/action. Do not guess, evade controls or make test submissions.
5. Inspect the result. Save exact employer acceptance evidence and receipt ID if
   present. Only then set `SUBMITTED` / `submitted_confirmed`. A click, disabled
   button, HTTP success, upload or promised email is not sufficient by itself.
6. For a timeout/crash/ambiguous result, keep `UNRESOLVED`. Check authorized receipt
   sources before another attempt. Do not blindly resubmit or clear the reservation.

If a required account/login is unavailable, ask the person to complete or authorize
that access as appropriate. Retrieve a verification code only if the relevant
inbox access and application route are authorized. Installed access alone is not
authorization. Never collect credentials into the skill's files.

When browser/submission tools are unavailable, finish supported documents and
answer maps, link the real application page, and label the application unsubmitted.
Do not switch to a simulated provider and present it as execution.
